# 7단계 서비스화 (Streamlit 화면과 로그 저장)

작성일 2026-10-06, 갱신 2026-10-08(서비스용 데이터 재수집·색인·칸 추출과 전환 점검). 중간점검의 계획은 "서비스화(Streamlit 화면, 로그 저장), 개선 실험 뒤 진행, 서비스용 데이터도 그때 다시 수집"이다. 이 문서는 지금까지 만든 것과 점검 결과, 남은 것을 적는다. 이력서 비교(확장)는 이번 범위에 넣지 않았다.

## 구성

| 파일 | 하는 일 |
|---|---|
| `src/rag_engine.py` | 질문 1개를 최종 파이프라인으로 처리해 답변·출처·처리 방식·토큰·비용·응답 시간을 돌려준다. `run_eval.py`의 함수를 가져다 쓰되 데이터셋(`eval` 또는 `service`)과 기준일을 바꿔 끼운다 |
| `src/log_db.py` | 질문마다 한 줄을 SQLite(`data/service_log.db`)에 저장한다. 요약과 공개용 CSV 내보내기 포함 |
| `src/app.py` | Streamlit 화면. 사이드바에서 직무·신입 필터나 공고 하나를 고르고 질문한다 |
| `src/check_engine.py` | 평가셋 30문항을 엔진으로 돌려 6단계 결과와 맞는지 보는 회귀 점검 |

## 처리 흐름 (엔진)

실험으로 정한 설정을 질문 하나씩 처리하도록 묶었다(`docs/step6_experiment_log.md`).

1. 공고를 골랐으면 그 공고 전체를 근거로 넣는다 (1단계)
2. 아니면 질문을 조건(학력·재택·마감일·기술 등)으로 해석해 공고별 칸으로 코드 필터링한다 (3단계)
3. 조건이 없으면 질문의 기술 표기에 동의어를 덧붙여 검색한다 (2단계). 회사 2곳 이상 신입 비교나 조건 없는 필터 질문이면 공고마다 질문이 묻는 항목 청크를 가져오고 (6단계), 그 밖에는 질문과 가까운 청크 top-10을 가져온다 (top_k=10, 순수 검색에서 적중률 76% → 92%)
4. 점핏 분류와 본문이 다른 공고는 그 차이를 근거에 붙이고 (4단계), 답변 지시문 v2로 답한다 (5단계)
5. 답변이 표시한 공고 중 실제로 있는 공고만 출처로 돌려주고, 마감 여부는 기준일로 계산한다

화면에서는 직무·신입 필터를 안 골라도(검색 범위 "전체") 조건 해석을 켜서 "재택 되는 곳 있어?" 같은 질문을 코드 필터로 처리한다.

## 화면

- 사이드바: 직무(전체/백엔드/프론트엔드), 신입 공고만, 공고 하나만 골라 묻기(마감 공고는 목록 뒤쪽), 선택한 범위와 이번 접속의 질문 수·비용
- 질문하기 탭: 예시 질문 5개, 채팅 입력, 답변, 근거 공고 목록(회사·공고명·항목·마감일·상태·점핏 링크), 처리 방식·응답 시간·비용·기준일, 마감 공고가 근거에 있으면 경고, 👍/👎 피드백
- 로그 탭: 질문 수, 총 비용, 평균 응답, 피드백 수, 오류·마감 공고 출처·인용 확인 실패 건수, 처리 방식별 건수, 최근 100건
- 공고 원문은 재배포하지 않는다는 조건 때문에 화면에 인용 문장을 보여주지 않는다. 인용은 로그(비공개 DB)에만 남는다.
- 오류가 나면 "답변을 만들지 못했습니다" 안내를 보여주고 오류 내용은 로그에 남긴다. 화면은 계속 동작한다.

## 로그 (SQLite)

테이블 `query_log`: 시각, 데이터셋, 기준일, 질문, 검색 범위, 처리 방식, 답변, 출처(JSON), 원문 인용(JSON), 인용 확인 수, 마감 공고 수, 모델, top_k, 공고별 검색 수, 지시문 버전, 입력·출력 토큰, 비용, 응답 시간(ms), 오류, 피드백(1/-1), 피드백 메모.
DB 파일은 인용 문장(공고 원문)이 들어 있어서 `.gitignore`에 넣었다. 공개용으로는 `python src/log_db.py --export 파일.csv`가 답변·인용·질문 원문을 뺀 CSV를 만든다.

## 조건 해석 확장 (7단계 중 추가)

앱에서 써 보니 "서울에서 일하는 곳만 알려줘"가 지원하지 않는 조건이라 검색(top-10 청크)으로 처리되었다. 신입 범위(14건)에서는 정답 8곳 중 7곳(드림어스컴퍼니 누락), 범위가 전체(101건)이면 정답 55곳 중 3곳만 나왔고 사용자는 누락을 알 수 없었다. 그래서 조건 해석(`run_eval.py`의 `PARSE_SYSTEM`·`PARSE_SCHEMA`)에 세 항목을 추가했다.

| 추가한 조건 | 처리 | 비고 |
|---|---|---|
| `location` 근무지 | 질문에서 뽑은 지역명이 공고 주소(`postings.csv`의 `location`)에 들어 있으면 통과. 시·도는 짧은 이름(서울, 경기…), 구·시, 동네·역 이름(판교, 가산)도 가능. "서울특별시" 같은 표기는 별칭표(`LOCATION_ALIAS`)로 맞춤 | 칸 추출 없이 기존 주소를 그대로 씀. 지역명은 "서울이나 경기"처럼 목록이면 OR |
| `newcomer_only` 신입 | 질문에 신입 공고만 찾는다는 뜻이 있으면 점핏 신입 분류만 통과 | 사이드바에서 신입을 안 켜도 질문 속 "신입"이 반영됨 |
| `job` 직무 | "백엔드" 또는 "프론트엔드" 공고만 통과 | 위와 같음 |

- 신입·직무는 **다른 조건 없이 이것만 있으면 조건으로 보지 않는다**(`REAL_CONDITIONS`). "티엔에이치 백엔드 신입은 어떤 언어를 사용해 봤어야 해?" 같은 회사 질문이 조건 검색으로 바뀌지 않게 하려는 것이다.
- 필터 로직은 코드로 확인했다: 신입 + 서울 8곳, 전체 + 서울 55곳(둘 다 공고 표의 정답과 일치), 서울특별시 별칭 55곳, 판교 2곳, 신입 + 강남구 + 재택·유연 3곳.
- 파서 프롬프트가 바뀐 것이라 평가셋 30문항을 다시 점검했다(아래). **6단계까지의 실험 결과는 이전 파서 프롬프트로 측정한 값**이고 다시 측정하지 않았다.

### 전환 점검

`check_engine.py`는 `Engine("eval")`과 9/30 기준 정답으로 채점하므로 서비스용 데이터에는 쓰지 않는다. 대신 정답 채점 없이 "서비스용 데이터로 엔진이 제대로 동작하는가"를 점검했다. 점검 스크립트는 임시 폴더에서만 썼고 프로젝트에는 남기지 않았다.

**A. 코드 점검 (API 없음)**: 모두 통과.
- 엔진이 서비스 컬렉션(청크 1,002개, 공고 140건)과 칸 파일(140건)을 읽고, 공고 표와 공고ID가 일치한다. 기준일은 오늘(2026-10-08)이다.
- 기준일 상태는 진행 중 104, 조기 마감 10, 마감 26이다.
- 조건 필터 6종의 엔진 결과와 직접 집계가 일치했다: 재택·유연 49, 코딩테스트 17, 테스트 코드 11, 근무지 서울 65, 신입+판교 1, 10/15 이전 마감 20. 마감 공고는 결과에 섞이지 않았다.

**B. 스모크 질문 8개** (서비스용 데이터, 엔진 직접 호출, 합계 $0.0136, 평균 응답 6~43초)
- 정상: 회사 질문(티엔에이치 자격요건, 새로 들어온 26도라인 주요업무), 필터 질문 3개(재택·유연 49건, 서울 신입 9건, 코딩테스트 17건 모두 기대 공고와 정확히 일치, 인용 검증 재택 42/47·나머지 전부 통과), 공고 선택 질문(복지), 문서에 없음 질문(연봉 "확인되지 않습니다").
- 이 질문 8개는 엔진을 직접 호출해서 `eval/usage_log.csv`와 앱 로그 DB에 **기록되지 않았다**. 누적 비용에는 포함되지 않은 $0.0136이다.
- 질문 비용은 예상($0.004)보다 높았다. 재택 질문이 49건을 모두 설명해서 한 질문에 $0.0074가 들었기 때문이다. 조건에 맞는 공고가 많은 질문은 비용과 응답 시간(42.6초)이 크다.

**발견·수정한 오류: 조기 마감 공고가 답변에서 "진행 중"으로 표시됨**
- 조기 마감 공고(휴먼에스 55162648) 질문에서 출처 목록은 마감 공고로 잡았는데 답변 문장은 "상태: 진행 중"이라고 했다.
- 원인은 `run_eval.py`의 답변 근거 머리글이 저장된 상태를 "진행 중"으로 고정해 마감일로만 계산한 것이다. 평가용 스냅샷 공고는 전부 진행 중이라 평가에는 영향이 없었고, 서비스용에서만 나타난다.
- 수정: 저장된 상태(`POSTINGS[...]["status"]`)를 함께 넘긴다 (커밋 `4b9c28d`). 평가용 컬렉션 청크 729개로 만든 근거 문장이 수정 전·후 **바이트 단위로 같음**을 확인했다. 서비스용은 표시가 바뀌는 공고가 정확히 조기 마감 10건이고, 엔진의 출처 상태와 근거 문장 상태가 모든 공고에서 일치한다.
- 수정 뒤 같은 질문을 LLM에 다시 던져 보지는 않았다(약 $0.0005). 근거 문장이 "조기 마감"으로 나오는 것까지만 코드로 확인했다.

## 한계

- `run_eval.py`의 전역값(공고 표, 기준일, 지시문 속 날짜)을 바꿔 쓰므로 한 프로세스에서는 한 번에 하나의 데이터셋만 쓸 수 있다. 평가 코드를 건드리지 않으려고 택한 방식이다.
- 앱은 서비스용 색인이 있으면 서비스용 데이터(기준일은 실행한 날)로, 없으면 평가용 데이터로 동작한다 (`RAG_DATASET`로 고정할 수도 있다). 서비스용 데이터는 10/08 수집본이라 시간이 지나면 다시 수집·색인해야 한다. 서비스용 정답 기준 평가셋은 없어서, 서비스용 정확도 수치는 없다.
- 질문 한 건 응답이 6초 안팎이고 길면 20초 넘게 걸린다(조건 해석과 답변 두 번의 LLM 호출).
- 범위가 전체인 조건 질문은 경력 공고까지 포함해 답한다(예: 재택 41건). 신입만 보려면 사이드바에서 필터를 켜야 한다.
- **조건 해석이 지원하지 않는 조건**은 청크 검색(top-10)으로 넘어가서, 정답 공고가 많으면 일부만 나오고 사용자는 누락을 알 수 없다(근무지 질문에서 55곳 중 3곳만 나온 것과 같은 문제). 로그 기준으로 확인한 것이 아니라 코드(`run_eval.py`의 `PARSE_SYSTEM`·`apply_conditions`)와 공고 표 칸을 대조해 정리한 목록이다.
  - 지원하는 조건(9개): 4년제 졸업 불필요, 마감일 이전, 재택·유연근무, 기술, 테스트 코드, 코딩테스트·과제 전형, 근무지, 신입, 직무(백엔드·프론트엔드)
  - 미지원, 데이터에 칸이 이미 있어 추가하기 쉬운 것: 경력 연차(`career_min`·`career_max`), 학력 세부(`education`), 상시채용(`closed_at`), 마감 임박·이후(`closed_at`), 회사(`company`), 점핏 기술 태그(`tech_stacks`), 풀스택 등 직무 세분화(`job_categories`), 게시일(`published_at`)
  - 미지원, 본문에서 칸을 뽑아야 하는 것: 연봉, 복지(식대·스톡옵션·교육비·장비), 회사 규모·업종·투자 단계, 병역특례, 고용 형태(정규직·계약직·인턴), 자격증·영어·포트폴리오 우대, 전형 단계
  - 질문에 지원 조건과 미지원 조건이 섞이면(예: "서울 신입 중 연봉 4천 이상") 미지원 조건은 조용히 무시된다.
  - 대응 후보: 필터로 못 거르는 조건에는 "목록이 불완전할 수 있다"는 경고를 답변에 붙인다 / 칸이 있는 경력 연차·상시채용·회사부터 조건을 추가한다. 아직 어느 쪽도 하지 않았다.
