# 개선 실험 기록 (단계별 누적)

각 단계는 이전 단계의 기능을 켠 채로 새 기능을 하나 추가해 다시 측정한다. 비교 대상은 직전 단계다.
공통 조건: 전략 B, top-5, 답변·채점 gpt-6-luna, 프롬프트 v1, 채점 기준 v2, 평가 기준일 2026-10-02.

## 검색 적중률을 읽는 법

- 검색 적중: 정답 근거 청크(공고ID/항목)가 검색된 top-5 안에 하나라도 있으면 O.
- 1단계는 `공고 선택` 14문항(A05~A10, A19, N01~N03, N05, T02, T03, T05)에 검색 없이 그 공고의 청크를 전부 넣는다. 정답 청크가 항상 들어가므로 적중률이 100%로 부풀려진다. 그래서 이 14문항은 검색 적중 칸을 비우고 집계에서 뺀다.
- 분모 계산: 검색 적중률은 정답 근거가 있는 문항만 센다. 문서에 없음 N01~N05는 정답 근거가 없어 처음부터 빠지므로 기준선 분모는 30이 아니라 25다. 공고 선택 14문항 중 N01·N02·N03·N05는 이미 빠져 있어서 실제로 더 빠지는 것은 10문항(A05~A10, A19, T02, T03, T05)이다. 25 − 10 = 15.
- 분모가 달라지므로 기준선의 원래 수치(76.0%, 19/25)와 1단계의 수치(73.3%, 11/15)는 비교할 수 없다. 기준선 채점표에서 같은 15문항만 다시 계산하면 11/15 = 73.3%로, 1단계와 같다. 위 표는 이 15문항 기준으로 통일했다.
- 이후 단계의 검색 적중률은 이 15문항 기준으로 비교한다.

## 1단계: 공고 선택 시 공고 전체 투입

- 바꾼 것: `src/run_eval.py --full-posting`. 검색 범위가 `공고 선택: ID`인 문항은 임베딩 검색 대신 그 공고의 청크 전부를 항목 순서대로 근거에 넣는다.
- 결과 파일: `eval/results/2026-10-06_B_k5_gpt-6-luna_full.csv`, 비용 $0.0049
- 대상 14문항의 변화: 개선 3 (A09 부분→정답, A10 오답→정답, T03 부분→정답), 악화 1 (T02 부분→오답), 유지 10
- 대상 밖 변화: A14 부분→오답. 검색 결과가 같은 문항이라 LLM 답변의 변동으로 본다. 문항 1개 차이(약 1.7%p)는 노이즈일 수 있다.
- 채택. 공고 선택형에서 검색 누락(A09·A10)이 사라졌다.
- 남은 문제
  - T02(직무 분류와 본문 조건이 다름)는 공고 전체를 넣어도 틀린다. 4단계(점핏 분류와 본문 조건이 다르면 명시) 대상이다.
  - 최신성은 그대로다. A19는 이미 정답이었고, T04(범위가 전체)·A20(조건 찾기)은 이 단계로 바뀌지 않는다.

## 2단계: 기술 동의어 사전

- 바꾼 것: `data/tech_synonyms.json`(53개 그룹)과 `src/run_eval.py --synonyms`. 질문에 기술 표기가 있으면 같은 기술의 다른 표기를 **검색용 임베딩 질문에만** 덧붙인다. LLM에는 원래 질문이 그대로 간다. 1단계 옵션(`--full-posting`)을 켠 채로 실행.
- 결과 파일: `eval/results/2026-10-06_B_k5_gpt-6-luna_full_syn.csv`, 비용 $0.0046
- 문항별 변화
  - **T01(스프링) 오답→정답, 검색 X→O**: 질문의 "스프링"에 Spring 계열 표기가 붙어 정답 청크가 검색됐다. 이 단계의 목표가 이뤄진 유일한 문항이다.
  - A12 정답→부분, A03 부분→정답, A14 오답→부분: 검색 결과가 바뀌지 않았거나(A03, A14) 근거 재현율이 같다(A12 1/2). LLM 답변의 변동으로 본다.
  - 답변 정확도 +6%p 중 검색 개선으로 설명되는 것은 T01의 +4%p뿐이고, 나머지 +2%p는 노이즈로 본다(문항 1개 = 약 2~4%p).
- 채택. 검색 적중률 11/15 → 12/15.
- 사전 설계 결정
  - **관련 기술은 동의어로 묶지 않는다.** JPA–Hibernate, iOS–Swift는 엄밀한 동의어가 아니라서 각각 독립 항목으로 두고, `_관련 기술`에 기록용으로만 남겼다. 질문 확장에도 쓰지 않고, 답변에서 같은 기술이라고 말하지 않는다.
  - **평가 문항과 겹치는 항목이 있다.** "테스트 코드"(A13)와 "CI/CD"는 일반 개발 용어로 포함했다. 사전은 공고 기술스택 빈도 기준으로 만들었고, 평가 문항에 안 나오는 기술도 넣었다.
  - **한글 부분 일치 오탐 발견·수정(2회).** T04 "**인공지능**팩토리"의 회사명이 AI 그룹에 일치해 검색 질문이 바뀌는 것을 실행 전에 확인했다. 처음에는 AI 그룹에서 한글 "인공지능"을 뺐지만, 그러면 사용자가 "인공지능을 활용해 본 경험"이라고 물어도 확장되지 않아(AI로 쓴 질문만 확장되는 한쪽 방향 문제) 되돌렸다.
  - 최종 규칙: 영문 표기는 단어 경계로, 3자 이하는 대소문자도 구분한다. 한글 표기는 2자 이상이고 **바로 뒤가 한글이 아니거나 조사·어미(을·를·이·가·은·는·의·로·에·도·만·과·와·랑·으로·에서·경험·관련·개발·써·쓰)일 때만** 일치로 본다. "인공지능을 활용…"은 확장되고 "인공지능팩토리…"·"인터뷰"는 확장되지 않는다.
  - 한계: 회사명이 사전 표기로 시작하고 뒤에 조사처럼 보이는 글자가 오면 오탐이 남을 수 있다. 평가셋에서는 확장 문항이 이 수정 전후로 같아(A05·A06·A12·A13·A15·T01) 재측정하지 않았다.
- 남은 문제: A11(학력), A16(공통 요구), A20(마감일)은 동의어로 풀리지 않는다. 3단계(조건 코드 처리) 대상이다.

## 3단계: 조건 찾기를 코드로 (공고별 칸 추출 + 코드 필터)

- 바꾼 것
  - `src/extract_fields.py`(새 파일)가 공고별 칸을 뽑아 `data/posting_fields_eval.csv`에 저장한다. 재택·유연근무(`remote_work`, `flexible_hours`)는 LLM 1회 추출(고정 스키마, 근거 문장 원문 일치 검증), 기술스택(필수·우대)·테스트 코드·코딩테스트는 규칙(동의어 사전 재사용)으로 뽑는다. 학력·마감일·신입 여부는 `postings.csv`에 이미 있는 칸을 쓴다.
  - `src/run_eval.py --structured`: `검색 범위`가 `필터:`인 문항만, 질문을 조건 JSON으로 해석(LLM) → 코드로 필터(기준일에 진행 중인 공고만, 검색 범위 안) → LLM은 걸러진 공고를 설명만 한다. 조건이 없으면 기존 검색으로 처리한다(A16).
- 결과 파일: `eval/results/2026-10-06_B_k5_gpt-6-luna_full_syn_struct.csv`
- 비용: 추출 $0.0154 + 평가 $0.0166 (기록된 값). 코드 오류로 첫 평가 실행이 중단되어 그 실행의 API 비용(약 $0.017로 추정)은 처음에 기록되지 않았고 보정 행으로 추가했다.
- 새 지표: 필터 정밀도 100%, 필터 재현율 100% (8문항 모두 정답 공고와 정확히 일치)
- 문항별 변화 (2단계 → 3단계)
  - A11 오답→정답, A12 부분→정답, A20 부분→정답: 코드 필터가 정답 공고만 정확히 걸러 냈다. A20이 정답이 되어 **최신성 83.3% → 100%**.
  - A14 부분→오답(LLM 채점, 사람 판정 정답): 필터는 6/6으로 정확하고 답변도 정답 6곳 전부이며 모두 신입 공고다. 그런데 채점 LLM이 "경력 공고를 섞었다"고 판정했다. 답변에는 경력 공고가 없어서 사람이 채점해 **정답**으로 판정했다(채점 LLM 오류, `eval/README.md` 기록). 그래서 3단계 답변 정확도는 LLM 채점 82.0%, 사람 판정 반영 86.0%로 둘 다 적는다.
  - A13, A15, A18, T01은 이미 정답이었고 유지.
  - 필터 밖 문항의 변화(A03 정답→부분, T02 오답→부분)는 검색·입력이 같아 LLM 변동으로 본다.
- 이 단계에서 남은 것
  - **A16**("신입 백엔드 공통 요구")은 조건이 아니라 요약이라 필터가 비어 검색으로 돌아가고, top-5가 공고 1건에 몰려 "공통 요구 확인 불가"로 오답이다. 여러 공고를 고르게 가져오는 방식이 필요하다.
  - **T04**는 이미 정답이어서(최신성의 나머지 문항) 3-b(공고 식별)의 필요성을 다시 확인해야 한다. 지금 정답은 검색이 우연히 맞힌 것일 수 있다.
- 주의
  - 추출 규칙과 사전은 평가 정답을 본 뒤 만들었다. 필터 정밀도·재현율 100%는 이 영향을 받았을 수 있어, 무작위 20건(시드 42)의 재택·유연근무 칸을 근거 문장과 대조해 확인했고(오류 없음), 아래처럼 반대쪽 누락도 규칙으로 점검했다. 기술스택·테스트 코드·코딩테스트 칸은 규칙이라 사람 검수 표를 아직 만들지 않았다.
  - 재택 추출: LLM이 N으로 둔 공고에서 관련 키워드를 규칙으로 훑어 보니 누락 후보는 모바일 "하이브리드 앱" 1건뿐이었고 실제 누락은 없었다. Y 근거 문장 중 1개 공고(뮤팟)에서 문장 3개 중 1개가 원문과 글자가 달랐다(판정은 맞음).
  - 문항 수가 적어 3단계 수치도 오르내림 폭이 크다.

## 4단계: 점핏 분류와 본문이 다르면 명시

- 바꾼 것
  - `src/extract_fields.py --career`: LLM이 본문(주요업무·자격요건·우대사항)에서 기대 최소 연차(`body_career_min`)를 뽑고, 불일치는 코드가 판정한다(`career_mismatch` = 본문 기대 최소 연차 > 점핏 경력 최소 연차). 기존 칸은 다시 뽑지 않고 열만 추가했다(`data/posting_fields_eval.csv`).
  - `src/run_eval.py --diff-notes`: 답변 근거에 들어간 공고 중 불일치가 있으면 `[분류-본문 차이]` 블록(예: "점핏 경력 분류는 신입이지만 본문은 경력 3년 이상 수준을 기대한다")을 근거 앞에 붙이고, 차이가 있을 때만 답변 규칙 2개(차이를 밝힌다, 점핏 분류만 보고 단정하지 않는다)를 프롬프트에 추가한다. 조건 필터에서 기술을 물은 문항은 "점핏 태그에는 있으나 본문에는 없어 필터에서 제외된 공고"를 참고 공고로 함께 붙인다.
- 결과 파일: `eval/results/2026-10-06_B_k5_gpt-6-luna_full_syn_struct_diff.csv`
- 비용: 추출 $0.0086 + 평가 $0.0171
- 추출 검수: 101건 중 본문에 최소 연차가 있는 공고 70건, 점핏 분류와 불일치 4건(인텍에프에이 3년, 코즈코리아 3년, 지피에이코리아 5년, 엘아이지시스템 5년). 4건 모두 근거 문장을 확인해 실제 불일치로 확인했다. 신입 14건 중에서는 코즈코리아만 표시되고, 보스반도체의 "경력 5년 이하"(상한 표현)는 올바르게 비어 있다. 근거 문장은 모두 원문과 일치했다.
- 점수 변화: 답변 정확도 82.0% 그대로(문항별 판정 변화 없음), 근거 표시 정확도 94.0% → 92.0%, 출처 정확도 100% → 99.0%(N05의 인용 1건이 원문과 달라서, 차이 블록과 무관한 LLM 변동). **점수로는 개선이 없다.**
- 의도한 동작은 확인됐다
  - T02: 답변이 "점핏 분류는 신입이지만 본문은 경력 3~7년차 수준을 예상하고 신입 지원도 가능하다"고 바뀌어 필수 요소 3개 중 "3~7년차 수준 예상"이 들어갔다. 그래도 **부분**인 이유는 필수 요소 "출시 경험 요건"이 여전히 빠졌기 때문이다(분류-본문 차이와는 다른 문제, 답변 완결성).

- 부작용
