# 개선 실험 기록 (단계별 누적)

각 단계는 이전 단계의 기능을 켠 채로 새 기능을 하나 추가해 다시 측정한다. 비교 대상은 직전 단계다.
공통 조건: 전략 B, top-5, 답변·채점 gpt-6-luna, 프롬프트 v1, 채점 기준 v2, 평가 기준일 2026-10-02.

## 검색 적중률을 읽는 법

- 검색 적중: 정답 근거 청크(공고ID/항목)가 검색된 top-5 안에 하나라도 있으면 O.
- 1단계는 `공고 선택` 14문항(A05~A10, A19, N01~N03, N05, T02, T03, T05)에 검색 없이 그 공고의 청크를 전부 넣는다. 정답 청크가 항상 들어가므로 적중률이 100%로 부풀려진다. 그래서 이 14문항은 검색 적중 칸을 비우고 집계에서 뺀다.
- 분모 계산: 검색 적중률은 정답 근거가 있는 문항만 센다. 문서에 없음 N01~N05는 정답 근거가 없어 처음부터 빠지므로 기준선 분모는 30이 아니라 25다. 공고 선택 14문항 중 N01·N02·N03·N05는 이미 빠져 있어서 실제로 더 빠지는 것은 10문항(A05~A10, A19, T02, T03, T05)이다. 25 − 10 = 15.
- 분모가 달라지므로 기준선의 원래 수치(76.0%, 19/25)와 1단계의 수치(73.3%, 11/15)는 비교할 수 없다. 기준선 채점표에서 같은 15문항만 다시 계산하면 11/15 = 73.3%로, 1단계와 같다. 위 표는 이 15문항 기준으로 통일했다.
- 이후 단계의 검색 적중률은 이 15문항 기준으로 비교한다.

## 1단계: 공고 선택 시 공고 전체 투입

- 바꾼 것: `src/run_eval.py --full-posting`. 검색 범위가 `공고 선택: ID`인 문항은 임베딩 검색 대신 그 공고의 청크 전부를 항목 순서대로 근거에 넣는다.
- 결과 파일: `eval/results/2026-10-06_B_k5_gpt-6-luna_full.csv`, 비용 $0.0049
- 대상 14문항의 변화: 개선 3 (A09 부분→정답, A10 오답→정답, T03 부분→정답), 악화 1 (T02 부분→오답), 유지 10
- 대상 밖 변화: A14 부분→오답. 검색 결과가 같은 문항이라 LLM 답변의 변동으로 본다. 문항 1개 차이(약 1.7%p)는 노이즈일 수 있다.
- 채택. 공고 선택형에서 검색 누락(A09·A10)이 사라졌다.
- 남은 문제
  - T02(직무 분류와 본문 조건이 다름)는 공고 전체를 넣어도 틀린다. 4단계(점핏 분류와 본문 조건이 다르면 명시) 대상이다.
  - 최신성은 그대로다. A19는 이미 정답이었고, T04(범위가 전체)·A20(조건 찾기)은 이 단계로 바뀌지 않는다.

## 2단계: 기술 동의어 사전

- 바꾼 것: `data/tech_synonyms.json`(53개 그룹)과 `src/run_eval.py --synonyms`. 질문에 기술 표기가 있으면 같은 기술의 다른 표기를 **검색용 임베딩 질문에만** 덧붙인다. LLM에는 원래 질문이 그대로 간다. 1단계 옵션(`--full-posting`)을 켠 채로 실행.
- 결과 파일: `eval/results/2026-10-06_B_k5_gpt-6-luna_full_syn.csv`, 비용 $0.0046
- 문항별 변화
  - **T01(스프링) 오답→정답, 검색 X→O**: 질문의 "스프링"에 Spring 계열 표기가 붙어 정답 청크가 검색됐다. 이 단계의 목표가 이뤄진 유일한 문항이다.
  - A12 정답→부분, A03 부분→정답, A14 오답→부분: 검색 결과가 바뀌지 않았거나(A03, A14) 근거 재현율이 같다(A12 1/2). LLM 답변의 변동으로 본다.
  - 답변 정확도 +6%p 중 검색 개선으로 설명되는 것은 T01의 +4%p뿐이고, 나머지 +2%p는 노이즈로 본다(문항 1개 = 약 2~4%p).
- 채택. 검색 적중률 11/15 → 12/15.
- 사전 설계 결정
  - **관련 기술은 동의어로 묶지 않는다.** JPA–Hibernate, iOS–Swift는 엄밀한 동의어가 아니라서 각각 독립 항목으로 두고, `_관련 기술`에 기록용으로만 남겼다. 질문 확장에도 쓰지 않고, 답변에서 같은 기술이라고 말하지 않는다.
  - **평가 문항과 겹치는 항목이 있다.** "테스트 코드"(A13)와 "CI/CD"는 일반 개발 용어로 포함했다. 사전은 공고 기술스택 빈도 기준으로 만들었고, 평가 문항에 안 나오는 기술도 넣었다.
  - **한글 부분 일치 오탐 발견·수정(2회).** T04 "**인공지능**팩토리"의 회사명이 AI 그룹에 일치해 검색 질문이 바뀌는 것을 실행 전에 확인했다. 처음에는 AI 그룹에서 한글 "인공지능"을 뺐지만, 그러면 사용자가 "인공지능을 활용해 본 경험"이라고 물어도 확장되지 않아(AI로 쓴 질문만 확장되는 한쪽 방향 문제) 되돌렸다.
  - 최종 규칙: 영문 표기는 단어 경계로, 3자 이하는 대소문자도 구분한다. 한글 표기는 2자 이상이고 **바로 뒤가 한글이 아니거나 조사·어미(을·를·이·가·은·는·의·로·에·도·만·과·와·랑·으로·에서·경험·관련·개발·써·쓰)일 때만** 일치로 본다. "인공지능을 활용…"은 확장되고 "인공지능팩토리…"·"인터뷰"는 확장되지 않는다.
  - 한계: 회사명이 사전 표기로 시작하고 뒤에 조사처럼 보이는 글자가 오면 오탐이 남을 수 있다. 평가셋에서는 확장 문항이 이 수정 전후로 같아(A05·A06·A12·A13·A15·T01) 재측정하지 않았다.
- 남은 문제: A11(학력), A16(공통 요구), A20(마감일)은 동의어로 풀리지 않는다. 3단계(조건 코드 처리) 대상이다.
