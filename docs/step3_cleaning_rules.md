# 정제 규칙서 (3단계: 파싱·정제·청킹)

공고 원문(`data/raw/2026-09-30/{공고ID}.json`, 점핏 API 응답)을 청킹하기 전에 적용하는 정제 규칙입니다.
대상은 본문 6개 항목: `serviceInfo`(회사소개), `responsibility`(주요업무), `qualifications`(자격요건),
`preferredRequirements`(우대사항), `welfares`(복지), `recruitProcess`(채용절차).

## 조사 근거

사용 문서 101건을 포함한 raw 원문 104건 전수를 스캔해서 아래 패턴 빈도를 확인했습니다.

| 패턴 | 발견 건수(항목 기준) |
|---|---|
| 줄바꿈이 `\r\n` (Windows식) | 전체 |
| 보이지 않는 문자 (zero-width space류, non-breaking space) | 17건 |
| 탭 문자 | 18건 |
| 연속 빈 줄 3줄 이상 | 16건 |
| 항목 안에 URL 포함 | 22건 |
| 항목 안에 이메일 포함 | 3건 |
| 항목 안에 전화번호 포함 | 1건 |
| HTML 태그 | 0건 (없음) |

항목별 채움/길이 현황 (raw 104건, 빈 문서 판정에도 사용):

| 항목 | 빈 건수 | 채워진 건수 | 평균 길이 | 최대 길이 |
|---|---|---|---|---|
| serviceInfo | 3 | 101 | 453자 | 4,605자 |
| responsibility | 0 | 104 | 250자 | 2,027자 |
| qualifications | 3 | 101 | 187자 | 532자 |
| preferredRequirements | 3 | 101 | 211자 | 1,007자 |
| welfares | 3 | 101 | 349자 | 2,060자 |
| recruitProcess | 18 | 86 | 190자 | 1,100자 |

빈 3건은 이미 품질 기준으로 제외된 리베코이앤씨 공고 3개(54941019, 54940975, 54941009)와 일치합니다.
`recruitProcess`가 빈 18건(17%)은 별도 결함이 아니라 원래 채용절차를 기재하지 않은 정상 상태입니다.

## 공통 규칙 (6개 항목 모두 적용)

1. 줄바꿈: `\r\n` → `\n`으로 통일하고, 남는 `\r`은 제거한다.
2. 보이지 않는 문자를 제거한다: zero-width space류(`​`, `‌`, `‍`, `﻿`)는 삭제하고,
   non-breaking space(`\xa0`)는 일반 공백으로 바꾼다.
3. 탭 문자는 공백 1칸으로 바꾼다.
4. 각 줄 끝의 공백을 제거한다. 공백만 있는 줄은 빈 줄로 취급한다.
5. 연속된 빈 줄이 3줄 이상이면 빈 줄 1개로 줄인다.
6. 항목 전체의 앞뒤 공백을 trim한다.
7. **불릿 기호(•, -, *, ※, ■, ○, 숫자. 등)는 통일하지 않고 원문 그대로 둔다.**
   출처 정확도가 최우선 지표이므로 원문을 임의로 가공하지 않는다. 검색(임베딩)에는 기호 차이가 거의 영향을 주지 않는다.
8. **줄 앞 들여쓰기와 트리 기호("└" 등)는 그대로 둔다.**
   중첩 불릿·하위 항목의 계층 구조를 나타내므로 삭제하면 의미가 손실된다.
9. **URL·이메일·전화번호는 모두 원문 그대로 둔다.**
   회사가 채용 목적으로 공개한 연락처·링크이며 개인정보가 아니다.

## 빈 항목 판정 기준

정제 후 문자열이 다음 중 하나면 "빈 항목"으로 취급하고 청크를 만들지 않는다 (청크 통계표에 "해당없음"으로 집계).

1. 빈 문자열
2. **placeholder 값**: 정제 후 값이 `-`, `없음`, `해당없음`, `해당사항 없음`, `.` 중 하나와 완전히 같은 경우.
   사용 문서 101건 전수 조사에서 7건 발견 (예: 26도라인 3개 공고의 `welfares`가 `-` 하나뿐).
   실제 내용이 없다는 뜻이므로 빈 문자열과 동일하게 처리한다.

## 항목별 규칙

| 항목 | 규칙 |
|---|---|
| serviceInfo (회사소개) | 공통 규칙만 적용. `< 기업소개 >` 같은 장식용 헤더, `[유튜브]`/`[기사]` 같은 홍보 링크도 그대로 둔다. |
| responsibility (주요업무) | 공통 규칙만 적용. `1. 개발 (80%)` 같은 번호+비중 표시는 업무 비중을 나타내는 유의미한 정보이므로 유지한다. |
| qualifications (자격요건) | 공통 규칙만 적용. |
| preferredRequirements (우대사항) | 공통 규칙만 적용. |
| welfares (복지) | 공통 규칙만 적용. `1. 근무 환경`, `2. 성장 지원` 같은 번호 매김 소제목은 유지하고, 청킹 전략 B(길이 보정)에서 하위 분할 지점 후보로 활용한다. |
| recruitProcess (채용절차) | 공통 규칙만 적용. 빈 값(17%)은 정상이므로 청크를 만들지 않고, 청크 통계표에 "해당없음"으로 집계한다. |

## 예외 처리 방침

- **필드 간 내용 혼재**: 일부 공고는 점핏이 나눈 6개 항목 대신, 한 항목 안에 `[채용절차]`, `[근무조건]`,
  `[Culture]` 같은 자체 소제목을 넣어 여러 항목 내용을 몰아넣는다.
  예: 54907748의 `welfares`에 `[기본 제도]`/`[업무 환경]`/`[조직 문화]` 소제목이 함께 들어있음.
  이 경우 다른 항목(`recruitProcess` 등)이 비어 있어도 실제로는 다른 필드 안에 내용이 있을 수 있다.
  → **재배치를 시도하지 않고 원문 그대로 청크화**한다. 대신 청크 수동 검사표에 "필드-내용 불일치" 체크 항목을
  추가해서 사례를 기록하고, 4단계 평가에서 실제로 답변 품질에 영향을 주는지 확인한다.
- **기술스택 태그 정규화**: `techStacks` 태그의 대소문자 표기 불일치(`labview`→`LabVIEW`, `Etl`→`ETL`,
  `Mfc`→`MFC` 등)는 본문 정제와 별개로, 메타데이터 설계 단계에서 별도 매핑표로 처리한다.

## 마감 여부 판정

`postings.csv`와 청크 메타데이터의 `status`는 **수집 시점** 상태다. 수집 뒤 마감일이 지나도 `진행 중`으로 남는다.
(2026-10-02 기준, 9/30 수집본 사용 문서 101건 중 12건이 마감일이 지났지만 `진행 중`으로 남아 있음)

- 저장된 `status`는 고치지 않는다 (수집 기록을 그대로 보존, 평가 기준 데이터 9/30 고정).
- 검색·답변 단계에서는 `src/posting_status.py`의 `effective_status(closed_at, status, today)`로 판정한 값을 쓴다.
  - 저장된 `status`가 `마감`/`조기 마감`이면 그대로 / `closed_at`이 `상시`면 `진행 중` /
    `closed_at` < 오늘이면 `마감` (마감일 당일은 진행 중) / 그 외 `진행 중`
- 한계: 조기 마감(마감일 전에 내려간 공고), 마감일 연장, 신규 공고는 날짜만으로 알 수 없어 재수집해야 반영된다.
- 확인: `.venv\Scripts\python.exe src\posting_status.py [기준일]`로 기준일별 진행 중/마감 건수를 볼 수 있다.

## 결정 기록

| 결정 사항 | 선택 | 이유 |
|---|---|---|
| 불릿 기호 통일 여부 | 원문 그대로 유지 | 출처 정확도 우선, 검색 성능에 미치는 영향 미미 |
| recruitProcess 내 연락처(이메일·전화번호) 처리 | 그대로 유지 | 회사가 공개한 업무용 연락처, 개인정보 아님 |
| 필드 간 내용 혼재 시 재배치 여부 | 재배치하지 않고 수동 검사표에만 기록 | 사례가 더 모인 뒤(4~5단계) 자동 재배치 규칙을 결정하는 것이 안전 |
| 학력·근무지 등 공고 정보를 검색 대상에 넣을지 | 공고마다 "공고 개요" 청크(`overview`) 1개 추가. 청크 A 584→685, B 628→729 | 평가셋 A11(학력 조건 질문) 검수 중 발견: 학력·근무지가 본문 6개 항목에 대부분 없어 검색으로 찾을 수 없었음. 메타데이터 필터만으로는 자연어 질문을 처리할 수 없음 (`docs/step3_metadata.md` > 공고 개요 청크) |
| 수집 뒤 마감일이 지난 공고 처리 | 저장값은 두고, 답변 시점에 `closed_at`과 오늘 날짜로 판정 | 지표 1순위가 최신성. 재수집 없이 서버 요청 0회로 반영 가능하고, 평가 기준 데이터(9/30)를 흔들지 않음. 재수집 방식은 조기 마감까지 잡지만 서버 요청이 필요해 서비스화 단계에서 다시 검토 |
