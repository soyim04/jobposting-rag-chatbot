# 정답지 점검 결과와 처리 계획

작성일 2026-10-07. 강사님 피드백(아래)에 따라 문제가 된 문항을 다시 분류하고, 처리 계획을 정리했다. 아직 정답지·채점 코드는 바꾸지 않았다. 수치는 전략 B, 채점 기준 v2, 평가 기준일 2026-10-02 기준이다.

## 1. 강사님 피드백

문항마다 정답지가 틀린 것인지, 답이 부족한 것을 정답지 탓으로 돌리는 것인지 가린다.

| 분류 | 처리 |
|---|---|
| 1. 정답지가 틀린 경우 | 정답지를 고친다 |
| 2. 정답지 탓이 아닌 경우 | 챗봇 답을 고친다 |
| 3. 애매한 경우 | 보고한다. 어떻게 묻느냐에 따라 답이 달라진다 |

규칙
- 정답지는 **질문만 보고** 고친다. 챗봇 답을 보고 고치지 않는다.
- 정답지를 고쳤으면 **처음 버전부터 전부** 새 정답지 기준으로 다시 채점한다.
- 고치기 전 점수와 고친 후 점수를 함께 적는다.

이 피드백 이전에 쓴 기준 변경 판단 중 챗봇 답을 근거로 삼은 것은 이 문서에서 모두 뺐다. 이미 기각한 채점 기준 v3(A04·A05 완화)는 "결과를 본 뒤 점수가 오르는 방향의 변경"이라는 이유였는데, 앞으로는 "질문만 보고 고치는가"로 판단한다.

## 6. 처리 계획

1. 3절의 정답지(A03, A04, A09, A14)를 질문만 보고 고친다. 
2. 고친 정답지로 **처음 버전부터 전부** 다시 채점한다. 질문이 그대로라 답변은 다시 만들지 않고 기존 결과 파일을 `run_eval.py --regrade`로 채점한다. 대상은 `eval/results/`의 기준선(전략 A·B)부터 7단계 엔진 점검까지 결과 파일 전체다. 30문항 한 번에 약 $0.01 수준이라 합계는 $0.2~0.3 이내로 추산한다(`eval/usage_log.csv`의 재채점 기록 기준).
3. 고치기 전 → 후 점수를 표기한다(아래 표 형식).
4. 3. 문항(A05, A16)은 보고로 처리한다. 2. 문항(정답지는 맞는데 챗봇 답을 고쳐야 하는 문항)은 재채점 후 남는 것이 있으면 개선 실험으로 처리한다.

전·후 점수 기록 형식 (`eval/README.md`의 기준 변경 기록에 추가할 내용, 재채점 후 채움)

| 변경 | 전 → 후 | 이유 |
|---|---|---|
| A03 필수 요소에서 시스템 프로그래밍 제외 | (재채점 후) | 질문이 언어를 묻는다 |
| A04 필수 요소에서 스톡옵션 제외(덧붙임으로 이동) | (재채점 후) | 질문이 연봉을 묻는다 |
| A09 필수 요소를 원문 표현으로 정정 | (재채점 후) | 원문에 없는 합성 표현 |
| A14 "섞이면 안 되는 내용"을 공고ID로 구체화 | (재채점 후) | 경력 공고가 어느 것인지 정답지에 없어 확인할 수 없다 |

확인할 것
1. A03은 "분야도 언어 요건에 포함"으로 읽을 여지가 있는데, 정답지를 고치는 쪽(1)으로 봐도 되는가.
2. A09 정정 후 제목의 "CRM"까지 필수로 볼지.
3. A14의 "섞이면 안 되는 내용"을 공고ID로 구체화하는 수정안이 맞는지. 이와 별개로 채점 LLM이 공고의 신입/경력 정보를 못 받는 채점기 문제를 어떻게 할지(채점 코드에 `newcomer` 정보를 넣을지, 사람 판정을 공식 수치로 쓸지).
4. A16은 정답지를 고칠지, 현재 기준을 두고 보고만 할지.
5. 재채점은 LLM 호출이라 영향 없는 문항의 판정도 흔들릴 수 있다. 전부 다시 채점해도 되는지, 바뀐 문항만 다시 채점하고 나머지는 기존 판정을 유지할지.

## 7. 채점 LLM 노이즈 (A14 외)

- "문서에 없음" 문항에서 답변에 마감일·상태 줄을 덧붙였다고 오답 처리하는 사례가 있다(5단계 N02, 6단계 N01). 그래서 이 지표가 80%로 나온 실행이 있고, 같은 설정의 다른 실행은 100%다.
- 이 흔들림을 수치에서 어떻게 표기할지(범위로 쓸지, 문항을 제외할지)도 확인이 필요하다.

## 8. 측정의 한계

- 같은 설정에서도 답변 정확도가 최대 8%p 차이 난다. 매 단계가 30문항을 처음부터 다시 실행(검색, 답변 생성, 채점)하므로 이전 단계에서 정답이던 문항이 정답으로 유지된다는 보장이 없다. 같은 설정 두 번이 갈린 사례가 있다(A04, A14, T03). 그래서 5단계부터는 두 번 실행해 두 번 모두 나아진 문항만 개선으로 센다.
- top_k 5 → 10의 순수 검색 설정 비교(66% → 평균 73%)는 k=5 기준선이 1회뿐이라 노이즈를 배제하지 못한다. 파이프라인 설정에서는 차이가 없었다.
- 6단계까지의 실험 수치는 조건 해석을 확장하기 전 파서 프롬프트로 측정했고 다시 측정하지 않았다. 확장 뒤 엔진 점검은 86.0%(평가 범위) / 80.0%(범위 전체)이다.
- 판정이 흔들리는 이유: 답변 생성과 채점 모두 LLM 호출에 temperature·seed를 고정하지 않았고(`run_eval.py`의 `chat_json`), 한 문구가 빠지느냐로 정답 / 부분이 갈리는 경계 문항이 있다.
- 개선을 평가셋을 보고 만들었다. 오답노트의 틀린 문항을 보고 고쳤고 같은 30문항으로 다시 쟀다. 항목 찾는 낱말 규칙은 평가 문항(A16·A17)을 본 뒤 만들었다. 평가셋 밖에서는 앱에서 근무지 질문이 정답 55곳 중 3곳만 나온 사례가 있었다.
- 지표별 분모가 다르다. 한 문항의 무게가 지표마다 크게 다르다.

| 지표 | 분모 | 비고 |
|---|---|---|
| 답변 정확도 | 25문항 (정답형 20 + 함정 5) | 정답 1 / 부분 0.5 / 오답 0 |
| 근거 표시 정확도 | 25문항 | |
| 최신성 | 3문항 (A19, A20, T04) | 83.3% = 2.5/3, 한 문항이 33%p |
| 문서에 없음 처리 | 5문항 (N01~N05) | 한 문항이 20%p. 80%는 4/5 |
| 검색 적중률 | 7문항 (A01~A04, A16, A17, T04) | 문서에 없음 5, 공고 선택 10, 조건 필터 8 문항을 뺌 |
| 출처 정확도 | 인용 문장 수 | 문항 수가 아님 (예: 145/145, 85/86) |

- 최종 리포트에서 "66% → 84~86%"처럼 범위로 보고하고, 최신성·문서에 없음은 3/3, 5/5처럼 분수를 같이 적어도 되는지 확인이 필요하다.

## 9. 6단계에서 하지 않은 실험

- 모델 변경(답변·채점 모두 gpt-6-luna), 임베딩 교체(text-embedding-3-small 고정), 청킹 추가 비교(전략 B 고정). 모델은 gpt-6.1-sol이 입력·출력 모두 20배 단가라 보류했다.

## 10. 서비스(7단계) 쪽
