# 평가셋 (4단계)

`eval_set.csv`는 평가용 9/30 스냅샷(`data/eval_snapshot_2026-09-30/`, 사용 문서 101건) 기준으로 다시 만든 평가셋입니다.
`eval_set.xlsx`는 1단계 초안(9/29 공고 12건 기준, 34문항)으로, 이력 확인용으로만 남겨 둡니다.

## 구성 (30문항)

| 분류 | 문항 수 | ID | 세부유형 |
|---|---|---|---|
| 정답형 | 20 | A01~A20 | 사실 확인 4 · 공고 선택 6 · 조건으로 찾기 5 · 비교·종합 3 · 최신성 2 |
| 문서에 없음 | 5 | N01~N05 | 공고에 없는 정보(연봉·코딩테스트·재택·회사 소개), 수집하지 않은 회사 |
| 함정 | 5 | T01~T05 | 표기 차이 · 분류-본문 불일치 · 다른 공고 섞임 · 마감 공고 · 부정 조건 |

## 평가 조건

| 항목 | 값 |
|---|---|
| 데이터 | `data/eval_snapshot_2026-09-30/postings.csv`, `data/chunks/eval/` (본문 청크 + 공고 개요 청크) |
| 평가 기준일 | **2026-10-02**. 마감 여부는 `effective_status(closed_at, status, "2026-10-02")`로 판정. 9/30 기준이면 101건이 모두 진행 중이라 최신성(지표 1순위)을 평가할 수 없어서, 12건이 마감 상태가 되는 10/02로 고정 |
| 필터 정의 | 신입 = `newcomer`가 참 (14건) · 백엔드 = `job_categories`에 "서버/백엔드 개발자" 포함 · 프론트엔드 = "프론트엔드 개발자" 포함 |
| 필터 결과 | 신입 14건 · 백엔드+신입 9건 · 프론트엔드+신입 5건 |

## 열 설명

| 열 | 내용 |
|---|---|
| `검색 범위` | `전체` / `공고 선택: 공고ID`(사용자가 공고를 고른 상태) / `필터: 조건`(위 필터 정의) |
| `정답` | 사람이 읽는 모범 답안 |
| `필수 요소` | 답변 정확도 채점 기준. `;`로 구분 |
| `근거` | 정답 근거 위치. `공고ID/항목키` 형식, `;`로 구분. 항목키는 `serviceInfo`·`responsibility`·`qualifications`·`preferredRequirements`·`welfares`·`recruitProcess`, 그리고 학력·근무지·마감일 같은 공고 정보가 든 `overview`(공고 개요) |
| `섞이면 안 되는 내용` | 답변에 들어가면 오답 처리하는 공고·내용 |
| `초안 문항` | 초안(`eval_set.xlsx`)의 문항 ID. 새로 만든 문항은 `신규` |

근거를 청크ID가 아니라 `공고ID/항목키`로 적는 이유: 청크ID는 전략(A/B)과 분할 번호에 따라 달라지지만 공고·항목은 같아서,
전략 A·B를 같은 정답으로 비교할 수 있다.

## 채점 기준

| 지표 | 계산 | 대상 |
|---|---|---|
| 검색 적중률 | top-k 검색 결과에 `근거`의 `공고ID/항목키`가 하나라도 있으면 적중. 함께 **근거 재현율**(근거 중 찾은 비율)도 기록 | 정답형·함정 25문항 (문서에 없음 5문항은 근거가 없어 제외) |
| 답변 정확도 | 정답(1) / 부분(0.5) / 오답(0). 필수 요소를 모두 말하면 정답, 일부만 말하면 부분, `섞이면 안 되는 내용`이 들어가면 필수 요소와 관계없이 오답 | 정답형·함정 25문항 |
| 근거 표시 정확도 | 답변에 표시한 출처 공고가 `근거`의 공고와 일치하는지. 틀린 공고를 표시하면 오답, 일부 누락이면 부분 | 정답형·함정 25문항 |
| 문서에 없는 질문 처리 | "확인되지 않습니다"처럼 모른다고 답하고 다른 공고 내용으로 지어내지 않으면 정답 | 문서에 없음 5문항 |

### 판정 규칙

- **질문 밖 정보**: `정답`과 `필수 요소`는 질문에 대한 답만 쓴다. 답변이 질문 밖 정보를 덧붙이면, 공고와 맞으면 감점 없음, 틀리면 오답 (A03 검수에서 정함).
- **일반 지식 추론**: 공고에 없는 일반 지식(예: Spring은 Java·Kotlin 기반)은 공고 근거와 질문을 잇는 데만 쓰고, 추론이라고 구분해 말해야 한다.
  추론을 공고 내용처럼 말하면 오답. 이런 문항은 `세부유형`에 "(추론 필요)"를 붙이고 `채점 메모`에 정답·부분·오답 조건을 적는다 (A05 검수에서 정함).

최신성(지표 1순위)은 A19·A20·T04의 답변 정확도를 따로 모아 보고한다.
LLM 자동 채점과 사람 채점을 같은 기준으로 하고, 두 결과의 일치율을 함께 기록한다.

## 채점표 (실행 결과)

평가를 실행할 때마다 `eval/results/{실행일}_{설정}.csv`에 문항별로 기록한다.

| 열 | 내용 |
|---|---|
| `id` | 문항 ID |
| `설정` | 청킹 전략, top-k, 임베딩·LLM 모델, 프롬프트 버전 |
| `검색 결과` | top-k 청크의 `공고ID/항목키` 목록 |
| `검색 적중`, `근거 재현율` | 위 기준 |
| `답변` | 챗봇 답변 원문 |
| `답변 판정`, `근거 표시 판정`, `문서에 없음 처리` | 정답 / 부분 / 오답 |
| `채점자` | LLM / 사람 |
| `메모` | 오답 사유 (5단계 실패 유형 분류에 사용) |

- **학력·근무지가 청크에 없었다** → 공고 개요 청크로 해결 (위 검수 기록 A11, `docs/step3_metadata.md` > 공고 개요 청크).
- **백엔드 신입 9건 중 서버 개발이 아닌 공고가 섞여 있다** (인프라 엔지니어, 임베디드, 설비 제어 S/W). 점핏 직무 분류를 그대로 쓴 결과로, A16에서 확인한다.
